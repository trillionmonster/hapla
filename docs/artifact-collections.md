# 按步骤展示生成文件

## 问题与依据

2026-09-11，视频制作过程中的片段在一轮回复结束后集中出现。原来的 `runCodex.ts` 等待整轮结束才扫描工作目录，上传函数又等待整个批次完成才返回，因此前面的工具步骤没有对应文件，而最后一次性追加许多独立卡片。

另一路 `apiSession.ts` 在助手文本完成后查找本地文件链接，将每个链接再转为一张文件卡。两路去重互不共享，同一媒体可能同时出现本地引用和上传引用。前端每个文件事件各占一行，单条消息内部的媒体网格无法收纳这些独立消息。Normal 历史加载还错误地将文件卡当作普通工具调用过滤。

## 展示约定

- 自动发现的过程文件按完成步骤收纳为文件集合，默认收起；不凭文件名判断成品，也不删除过程文件。
- 助手应在正文说明并链接需要交付的成片、报告或页面。明确引用的少量文件便于预览，批量引用也使用集合。
- 展开集合时每页最多挂载六个文件，翻页替换当前页，收起卸载预览。视频继续使用封面、时长、原始分辨率、比例及原文件大小；对话列表不挂载播放器。
- Markdown 和 HTML 保留文件预览入口。文件集合只组织附件，不改变正文内容。
- 旧记录没有来源信息时，只收纳相邻附件，不跨正文、用户消息、分支或运行记录猜测归属。

沿用现有 Hapla 的字体、主题颜色、图标和预览页面；此次调整针对对话信息组织，不重做品牌或导航。

## 数据与生命周期

文件协议新增可选 `artifact` 字段，包含 `origin`、`batchId`、`sourceId` 和原始 `path`。`origin` 区分自动发现与正文引用，不代表最终成品。旧记录仍可解析。前端归一化保留这些信息，文件时间使用发现步骤的时间，而非上传结束时间；普通目录扫描记录的是发现文件的检查点，不能反推实际生产工具。

CLI 在完成工具步骤或收到明确的生成完成事件时检查新文件，整轮结束仅补漏。文件版本只有在消息持久化确认后才标记送达；文件变化和失败应允许后续重试。工作区视频和音频优先传递文件引用，查看时读取原件，减少批量上传过程文件的等待。

会话级待交付账本先记录本次发现的全部候选，再以两个并发任务准备文件。文件交给消息 outbox 后立即释放准备任务，单独跟踪持久化确认；网络 ACK 不再挡住后续文件排队。单轮交付等待最多 30 秒，未提交候选仍留在账本，下一完成步骤或连接恢复时继续，原来的 turn、来源和时间不变。账本保存在当前会话进程中、最多 20,000 条，不承诺进程被终止后的未提交候选恢复。超过待扫描步骤队列容量的通用扫描归入补漏批次，不冒充某个具体工具的产物。

文件大小和修改时间稳定只能排除明显写入，无法证明一个暂停的生产进程以后不会继续写。生产任务应使用临时文件并原子重命名发布最终文件；媒体格式探测和读取前后检查用于降低误判，不能替代生产者的完成信号。
