# 长会话与多模态工作台设计

状态：源码、12345 部署及真实浏览器端到端验收均已通过  
适用范围：`hapla-web`、`hapla-server`、`hapla-cli` 之间的会话消息、媒体展示和文件下载  
设计参数：变化度 3、动效 2、信息密度 8

## 1. 目标

工作台必须同时满足四件事：长会话不会因一次性加载而拖垮手机；图片、音频和视频可以直接在消息流中辨认和预览；大媒体通过 HTTP Range 按需读取并可拖动进度；任何媒体都能以不占用整文件 JS 内存的方式下载。

本次保持现有深色、紧凑的开发工作台结构，不引入新的 UI 框架、转码集群、Kubernetes、对象存储或独立媒体服务。

## 2. 现状结论

| 能力 | 当前实现 | 结论 |
| --- | --- | --- |
| 消息列表 | Web 使用倒序 `FlatList`，首批渲染 12 条，窗口 7 个视口 | DOM 已虚拟化 |
| 历史同步 | 首次取最新 80 条，向上滚动再按稳定游标加载 80 条；活动窗口最多 600 个原始事件 | 服务端分页与客户端内存上限已生效 |
| 远程图片 | URL 或 Data URL 进入媒体画廊 | 可展示，已有懒加载、全屏和缩放 |
| 远程视频/音频 | 浏览器原生 controls + 统一查看器、下载及错误态 | 浏览器支持的编码可播放、拖动和下载 |
| 相对/绝对路径 | 只允许解析到当前会话工作区内，小文件受 8 MiB 内联上限保护 | 安全边界和手机内存边界同时生效 |
| 工作区文件下载 | 支持 File System Access 时流式落盘，否则使用明确的 Blob 回退 | 主流支持环境不要求 JS 持有整文件 |
| 服务端媒体 | `/files/*` 支持完整 GET、单 Range 与越界校验 | 具备 `206`、`Accept-Ranges`、`Content-Range` 和精确长度 |
| 生成媒体 | 回合差分快照自动发现图片、视频和音频并上传为服务端 URL | 不依赖模型输出路径或 Markdown；图片最大 25 MiB，视频/音频最大 60 MiB |

当前页面已有固定的消息活动窗口和内联预览上限；长历史不会在首次打开时全部进入 JS 堆。`512 MiB` 是工作区传输许可上限，不代表手机可安全内联预览同等大小的媒体，因此本地预览仍执行 8 MiB 硬限制，大媒体优先走服务端 URL 与 HTTP Range。

## 3. 信息架构和交互

### 3.1 消息时间线

- 初次进入只请求最新 80 个原始消息事件，按时间正序归约后以现有倒序列表展示。
- 距离历史端 2 个视口时自动请求更早的 80 个事件；加载状态占据固定高度，避免跳动。
- 实时消息只从最新游标增量获取，不再触发从 0 开始的全量补拉。
- 自动内存窗口预算为 600 个原始事件。到达预算后，时间线以可逆的历史窗口切换代替继续增长；另一端显示“返回最新消息”或“继续查看更早记录”。未解密页只保留在服务端，不进入浏览器堆。
- 每次窗口变化都从当前窗口的原始事件重建 reducer，避免把更早事件错误地追加到较新 reducer 状态。跨页工具调用保留 20 个事件重叠区；无法闭合的工具卡显示“上下文位于相邻历史页”，不伪造完成态。
- 用户离开会话后释放该会话的活动窗口；保留草稿、最新序号和分页游标，不保留媒体 Blob。

### 3.2 媒体卡片

媒体卡片沿用消息宽度，不制造大块空白：

- 单张图片按真实比例展示，限制在消息可用宽度和 70vh 内；超长图使用完整容器和 `contain`，不裁切。
- 多媒体在桌面为两列，在窄屏为横向吸附列表；每张卡的触控目标不少于 44 px。
- 视频缩略卡只加载 metadata，不自动播放；打开查看器后仍使用 metadata 预载，由用户播放触发数据读取。
- 音频使用紧凑卡片，保留系统级播放、倍速和辅助功能兼容性，不为了波形图解码整段音频。
- 全屏查看器顶部显示文件名、类型和当前位置；操作始终可见：下载、在新标签页打开、关闭。图片提供缩放复位，视频和音频使用原生进度条。
- 加载中、损坏、浏览器不支持、网络中断、重试和空资源均有独立状态。错误文案区分“资源不可达”和“编码不受浏览器支持”。
- 关闭查看器或媒体离开虚拟列表窗口时暂停播放并移除 `src`，释放解码器和网络连接。

### 3.3 路径和 URL

- `https://host/file.png`、Markdown 图片语法和独占一行的媒体 URL 直接进入媒体卡片。
- 相对路径与绝对路径先规范化，只允许当前会话工作区内的真实文件；越界路径显示安全错误。
- Codex `~/.codex/generated_images` 下生成的图片、视频和音频由 CLI 上传到服务端后替换成 URL，因此手机不需要访问开发机本地路径。
- 一般工作区文件继续通过加密 RPC 下载。小型图片可内联预览；大视频/音频在完成服务端中转协议前不得伪装成流式播放，界面应显示文件大小和下载入口。

### 3.4 自动媒体资产发现

- 每个 Codex 回合开始时记录当前工作区和 `~/.codex/generated_images/<threadId>` 中受支持媒体的路径、大小、修改时间和 inode 基线。
- 回合结束时重新扫描并只选择新增或内容发生变化的媒体；这条链路不读取模型回复，也不要求模型输出 Markdown。
- `.git`、`node_modules`、`dist`、`build`、缓存、覆盖率等生成噪声目录不参与扫描；最大深度 8、最多检查 20,000 个目录项、单回合最多投递 12 个媒体。
- Codex 生成目录按当前 thread 隔离，不扫描其他 thread；工作区文件必须经过 realpath 校验，符号链接不能越过工作区。
- 文件大小和修改时间连续稳定后才允许读取，避免上传仍在写入的半成品。上传以“真实路径 + SHA-256 内容摘要”去重，同一路径内容变化后仍可再次展示。
- 上传结果使用 Wire `file` 结构化事件传输；Web 将图片、视频和音频归约为 `agent-media`，直接交给 `MediaGallery`。普通文件继续使用文件卡，不执行 HTML，也不伪装成 Markdown。

## 4. 传输与容量边界

### 4.1 服务端 URL 媒体

- `/files/*` 与登录态文件路由实现单 Range：`bytes=start-end`、开放结尾和后缀 Range。
- 合法请求返回 `206`、`Content-Range`、`Content-Length`、`Accept-Ranges: bytes`；越界返回 `416` 和 `Content-Range: bytes */size`。
- 普通 GET 返回准确 `Content-Length` 和 `Accept-Ranges`。播放器拖动由浏览器自动发起后续 Range 请求。
- 下载直接使用同源 URL，不先读入 JS Blob。

### 4.2 明确限制

| 类型 | 本次产品边界 | 原因 |
| --- | --- | --- |
| 消息初始页 | 80 个原始事件 | 控制首次解密和首屏延迟 |
| 消息活动窗口 | 600 个原始事件 | 给手机 JS 堆留下媒体和编辑器空间 |
| 图片上传 | 25 MiB/张 | 与现有生成图片流程一致 |
| 生成视频/音频上传 | 60 MiB/个 | 与 100 MiB API body 限制匹配，单请求只传一个大媒体 |
| 工作区传输 | 512 MiB/文件 | 保留现有显式文件传输边界，不等同于预览安全上限 |
| Data URL 内联预览 | 8 MiB | 避免 Base64 多副本挤占手机内存 |
| 服务端 URL 播放 | 不设前端整文件内存上限 | Range 按需读取；实际受服务器磁盘、代理和浏览器编码能力约束 |

本次采用静态媒体的渐进式 Range 传输，不建设 HLS/DASH 自适应切片和转码。MP4 若 `moov` 位于文件尾部，浏览器仍可能先请求尾部；Range 可以支持它，但推荐生成 fast-start MP4。

## 5. 格式兼容策略

“扩展名可识别”不等于“所有浏览器一定能解码”。产品基线为：

- 图片：PNG、JPEG、GIF、WebP；AVIF 和 SVG 由浏览器能力决定。
- 视频：H.264/AAC MP4 与 VP9/Opus WebM 为验收基线；MOV、M4V、Ogg Video 显示为尽力支持。
- 音频：MP3、WAV、AAC/M4A、Ogg/Opus 为验收矩阵；FLAC 依浏览器能力。
- 不支持的编码不自动转码，必须给出下载和“在新标签页打开”退路。

## 6. HTML 与 Markdown 的边界

- Markdown 的标题、列表、任务列表、表格、代码、链接、图片、数学和 Mermaid 继续由既有渲染器负责；长代码和宽表横向滚动，不扩张页面宽度。
- HTML/MCP Apps 继续走沙箱 iframe，不把任意 HTML 注入消息 DOM。iframe 卸载时终止消息监听并释放资源。
- 媒体 URL 只进入媒体元素属性，不解释为 HTML。

## 7. 验收样例

自动化夹具覆盖：2000 条长会话、透明/超宽/超高/动画/损坏图片、10 秒与长时长音频、横屏/竖屏/4K 元数据视频、MP4/WebM、无音轨视频、不支持扩展、Range 首段/中段/尾段/越界、下载头、相对路径/绝对路径/越界路径，以及 320、390、768、1440 宽度。

必须提供以下证据：

1. API 分页测试证明初次不再全量拉取。
2. Range 路由测试证明 200、206、416 和字节内容正确。
3. 组件测试证明查看器操作、错误态、下载链接和资源清理存在。
4. 类型检查、全量单测和生产构建通过。
5. 可用浏览器自动化执行移动端滚动、拖动播放和下载样例；当前环境缺少 Chrome DevTools MCP 时，正式 CWV trace 单列为受阻，不影响其余功能验收，也不把替代指标冒充 CWV。

## 8. 实施顺序

1. 先补消息双游标 API 和客户端活动窗口状态。
2. 再实现通用 Range 响应并覆盖公开与登录态媒体路由。
3. 再重构媒体画廊工具栏、预载、下载和资源回收。
4. 最后扩展生成音频上传、收紧 Data URL 预览限制，并执行完整样例矩阵。
