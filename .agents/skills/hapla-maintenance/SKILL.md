# Hapla 项目维护

从仓库根目录工作。同一台机器可能同时有多个完整实例，以及共用中继的个人执行器。
先判定任务模式，再核验资源归属；不要根据容器名前缀推断所属 stack。

## 任务模式与正式更新边界

**默认全部视作开发迭代，使用 `dev-hapla` stack。只有用户明确声明要执行
“正式部署更新hapla”，才进入正式部署更新流程。** 提到触发语、讨论发布方案、
引用文档或日志不等于要求执行。普通的“更新 Hapla”“修复线上问题”“重启验证”
仍按开发迭代处理：可只读检查现场，修改、复现和运行验收放到 `dev-hapla`。

开发任务不得重建、重启、停止、替换正在使用的其他 stack 或执行器，不改变它们的
端口、入口、镜像标签、挂载、凭据或数据。开发验收通过后交付结果，不自动发布。
正式更新获授权时，也只操作用户指定的目标和范围，沿用下文的现场维护要求。
纯文档或静态修改无需为此启动服务，但不能用它们暗示已完成运行验收。

## dev-hapla 开发约束

- 先读 [开发环境](../../../docs/development.md)，检查 Git 变更、在线容器、
  stack/Compose 标签、完整配置文件列表、镜像、端口、卷和实际 bind mount。
  如果在线服务直接挂载待改源码，先准备独立开发 checkout/worktree，避免保存文件
  或构建产物触发在线环境变化。保留用户已有改动。
- 开发 stack 名固定为 `dev-hapla`。不存在时，在需要运行验证的开发任务中独立准备
  它的配置和资源；不接管其他 `dev-*` stack，不改名或复用在线部署。
  Compose 命令显式指定 `--project-name dev-hapla`、私有 env 和完整 `-f` 列表。
  当前 `./deploy.sh --instance dev-hapla` 会生成 `hapla-dev-hapla`，不能代替该项目。
- Web 和 Server 分别使用独立、互不相同的宿主机端口，并与所有已占用端口隔离；
  同时核对 Docker 发布端口和宿主机监听，冲突时改 dev 配置，不停止现有服务腾端口。
  默认绑定 `127.0.0.1`。容器内仍可使用 `web:80`、`server:3005`；只改 Web 端口
  不代表 Server 已完成隔离。将实际端口写入 dev 私有配置并验证映射。
- 使用 dev 专属镜像标签、网络、数据库、主密钥和工作区/账号状态卷，不覆盖在线镜像，
  不挂载在线数据库、工作区或认证目录。PGlite 数据目录仅允许 dev Server 一个写入者。
  dev 配置和现场记录放忽略的 `.runtime/dev-hapla/` 或 `artifacts/`；通用说明放 `docs/`。
- Hapla CLI 的运行、调试、登录、daemon 和真实 agent 验收全部放在 `dev-hapla` 的
  Docker 容器内；不在当前宿主机安装、链接或执行 Hapla CLI，也不在宿主机调用
  `pnpm cli`、`hapla` 或启动测试 daemon。宿主机可以编辑源码、管理 Docker 和运行
  不启动 Hapla 的文档/配置检查；应用依赖安装、构建及包级测试放在 dev 开发容器。
- CLI 使用独立容器状态路径，显式设置 `HAPLA_SERVER_URL=http://server:3005` 和
  dev 浏览器入口 `HAPLA_WEBAPP_URL`，避免默认值连到在线环境。Web 的浏览器请求
  使用 dev 公共地址或 dev Web 的同源代理，不能把 Docker DNS 名交给浏览器解析。
  不复制或挂载宿主机及其他用户的 `.hapla`、`.codex`、`.claude`；按 dev 账号配对登录。
- 容器内测试必须加载本次修改：重建 dev 镜像，或使用 dev 源码和独立依赖/输出目录。
  `deploy/Dockerfile.worker` 是运行镜像，不能假设它带有 pnpm、源码及开发依赖；需要
  源码调试时准备 dev 开发容器。Docker 不可用时继续可完成的静态工作并报告验证阻塞，
  不退回宿主机启动 CLI，也不借用在线 stack。

## 按任务读取

- 开发、迭代、构建和调试：读 [开发环境](../../../docs/development.md)，遵守上述边界。
- 配置、首次启动、部署失败：读 [一键部署](../../../docs/quickstart.md) 和
  [配置参考](../../../docs/configuration.md)。维护实现是 `scripts/selfhost.cjs`、
  `scripts/lib/selfhost.cjs`；`deploy.sh` 和 pnpm 别名共用此实现。
- 多实例、账号、执行器问题：读
  [环境隔离](../../../docs/environment-isolation.md)。模板是
  `deploy/compose.worker.yml` 和 `deploy/Dockerfile.worker`。
- Codex 追问、终端、历史问题或开发页面代理：读 [Web 交互](../../../docs/web-interaction-features.md)；
  代理依赖同版本 Web、Server 数据库迁移及 CLI daemon，在 dev 账号中验证句柄持久性、
  当前账号访问范围及 HTTP/WebSocket 转发。
  代理管理和共享需覆盖仅自己、全站已登录用户、公网凭密钥三档，以及非创建者不可编辑、
  密钥重置/撤销和旧授权失效。共享页面必须在每个句柄独立的预览来源运行，验证上游页面
  无法读取主站登录态，退出/切换账号时旧授权及长连接失效；只配置 dev 的预览域名，不在开发任务中修改正式 DNS、入口或凭据。
  首次提问要实际粘贴和选择图片后发送，检查非空上传、模型收到图片、失败保留草稿、
  重试复用已创建会话，并验证手机换行及中文输入确认不触发发送。
  Codex 自动注册代理还需通过实际 STDIO MCP 桥发现并调用注册/列表工具，不能仅验证
  HTTP MCP 端点；浏览器代理覆盖外部端口及多层 HTTP/HTTPS 转发。
  登录验收通过真实 Nginx 执行根路径链接、表单 POST、Cookie 及回跳，核对浏览器
  外部协议和端口不丢失；不能用 Node 静态服务的结果替代正式 Nginx 链路。
  追问控件还应验收菜单键盘操作、队列编辑失败时保留输入、窄屏旁问不遮挡输入框及深色模式。
  横屏设置/历史面板还须核对实际边界位于页头和输入区之间，滚动到首项并实际修改控件，
  不能仅通过 DOM 值断言或截图文件存在判断未被裁剪。
  前端变更按 [浏览器操作验收](../../../scripts/acceptance/README.md#frontend-interaction-acceptance)
  实际点击、输入、发送并核对执行结果；覆盖失败后保留输入、重试成功和状态持久化。
  发现缺陷后修复、重建并复测原操作序列，保留操作记录和录像；不能看完截图即结束。
  返回导航修复使用 `session-navigation.mts` 覆盖直接链接、刷新、切换会话、变更页返回对话
  再返回列表及手机横屏，逐项核对 URL 与列表可见性；不能仅验证按钮点击成功。
  手机端单独跑触控流程，覆盖新建与既有会话、弹层点按关闭、横屏、多行输入和低高度
  旁问停止入口；分别记录 Chromium/Android 与 WebKit/iPhone 模拟结果，不将模拟
  等同于实体设备、真实软键盘、系统粘贴菜单或 Safari App 验收。
  手机输入工具栏变更还需从“更多输入操作”打开设置、完整历史及附件选择器，验证
  有草稿时显式停止保留输入、发送后原位置重复点按不会误停任务，并检查旁问低高度
  收拢后的停止和关闭入口。
- Git 审阅、提交或检查点恢复：读 [编码工作台](../../../docs/coding-workbench.md)。
  使用 dev 专属 Git 仓库和本地 bare remote；浏览器回归可用本地 Responses 夹具驱动
  真实 Codex，不复制个人登录、不向真实代码托管平台创建测试 PR。恢复必须覆盖
  原生分支准备失败、其他会话占用、文件变化、暂存区保留和恢复后的原线程接续。
  工作台视觉改版还需检查浅/深色、手机首屏代码、文件列表展开、完整原始补丁与大差异
  窗口化渲染，并复跑暂存、提交、PR 失败保留草稿和回退后的继续提问。
- 会话状态、权限或恢复修复：读 [Web 交互](../../../docs/web-interaction-features.md)，
  用 `session-state.mts` 在双浏览器上下文验证换端设置、远端字段同步、分支拒绝、
  队列修订、503 后保留草稿和同 ID 重试；分别跑 desktop/Android Chromium/iPhone WebKit。
  `session-state-native.mts` 核验显式默认模型/思考重置。使用独立临时 Hapla/Codex
  状态和本地 Responses 夹具，构建/单测结束后再跑，避免 dist 被全局测试准备清空。
  手动和 daemon 恢复还需保留稳定根 ID、分支、原生参数及私有启动环境；不把环境值
  写入共享 metadata 或验收日志。
- 协议或业务修复：读 [仓库结构](../../../docs/repository-layout.md)、
  [测试说明](../../../docs/testing.md)，按需再读对应功能文档。
- R2 交付或网关：读 [Cloudflare](../../../docs/cloudflare.md)。外部文件服务独立维护，
  下载 Worker 是实验集成，不能仅凭本地检查宣称公网提速。

部署记录放在忽略的本地运行目录。

## 定位真实运行环境

先看 Git 变更及目标进程/容器，记录镜像、Compose 项目标签、配置文件路径、实际
挂载、网络、重启策略与状态。只读取必要字段，避免打印完整 `Config.Env`、原始
容器检查 JSON、访问令牌、签名 URL 或恢复密钥。

现有部署的实际挂载可能与持久 Compose 声明不同。现场维护必须对照两者，保留用户
当前的工作区和认证，不直接把新模板套到旧容器上。独立执行器共用网络是合理现象，
不能因此判断为端口冲突或跨项目污染；已停止的回退容器也不占用监听端口。

## 配置与部署

只有满足上述正式更新触发条件，才将本节用于正式环境。标准自托管实例使用
`./deploy.sh up --instance NAME`，按授权范围完成配置、构建和健康检查；开发环境
使用已核验的 `dev-hapla` Compose 配置，不能用默认实例命令替代。已有配置保留
主密钥；缺少配置却存在数据库卷时，恢复原配置，不能重新生成密钥接管旧数据。

首次 Hapla 配对和 Codex/Claude 登录由各账号完成。自动化只准备自己的配置与卷，
不复制另一个人的 `.hapla`、`.codex` 或 `.claude`。使用相同 `--instance` 执行
后续 status/logs/down/worker 操作。自定义本地覆盖文件需核对完整 Compose 文件列表。

既有环境更新先确认在线工作及备份：PGlite 必须保持单写入者，数据库冷备应在目标
Server 停止后进行，并保留原主密钥。只操作目标项目/服务，不执行全局 prune、
`down --volumes` 或删除其他项目目录。需要删除未授权的数据时，先准备明确对象再
向用户说明；普通构建、只读检查和已授权的更新继续执行。

执行器 daemon 使用 `start-sync` 作为前台进程。容器重启可能结束其会话子进程，
不能把宿主机 daemon 的交接能力等同于容器会话保活。按原 conversation/thread 标识
恢复原本在线的会话，不自动唤醒手动休眠会话，不发测试提问到真实用户对话。

正式更新时，若用户还明确要求更新既有宿主机 CLI，沿用其安装路径、服务和账号状态；
这不放开开发阶段的 Docker 约束。先核对 systemd 的 KillMode，避免更新 daemon 时
连带终止正在执行的会话；临时保活配置用后恢复。待机会话按原线程接续，活动会话
等空闲后再切换并记录结果。宿主机原生 Codex 的持久数据库可能比 dev 更新，不能
为对齐协议快照而直接降级；保留兼容的原版本，并验证实际线程恢复。

## 验证与交付

部署脚本或隔离模板变更运行 `pnpm test:selfhost`，覆盖密钥保留、私有配置、端口、
资源归属、两用户状态卷与 Compose 展开。新部署脚本可用测试里的隔离假 Docker
验证流程；不能用假 Docker 或模板校验代替真实上线健康结果。
修改执行器镜像后，构建实际镜像并运行 `node scripts/worker-image-smoke.cjs IMAGE`；
它不使用账号、不联网、不发模型请求，验证非 root 状态路径和原生 PTY。

代码变更在 dev 开发容器内运行相关包测试及构建；文档运行 `pnpm check:docs`，架构运行
`pnpm check:boundaries`。协议检查要求快照对应的 Codex 版本，不能为消除版本差异
而直接重写快照。改动未涉及真实 agent 行为时，不启动付费模型验收。

开发运行验收验证 dev Web、Server `/health`、容器 CLI、测试账号机器在线及本次功能，
并对比操作前后的在线容器标识、启动时间、镜像和端口，确认开发操作未改变在线 stack。
正式更新获授权时才验证并更新对应正式目标。报告任务模式、改动、实际检查结果、
仍未验证的环节、使用的 stack/服务和 dev Web/Server 端口；配置只报告路径和权限。
实现变化时同步维护本 Skill 和它引用的当前文档。

获授权提交推送后，读取该提交的 GitHub Actions 最终状态。区分本地检查、推送成功
与远端 CI 通过；远端失败时检查日志并修复，推送后确认新提交的运行结果，不重写
旧提交历史或伪造成功状态来隐藏失败记录。
